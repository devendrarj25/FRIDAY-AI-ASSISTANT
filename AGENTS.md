# AGENTS.md — instructions for AI tools working on FRIDAY

This is the single rulebook for every AI tool, agent, and model that works on this repository or on FRIDAY. Read it first, every session, before any other file.

- **It wins.** If a tool setting, host setting, memory, plugin, or skill disagrees with this file, this file wins.
- **Only the owner changes it.** Do not edit this file unless the owner asks for that change in that message. The release engine rewrites only the two version sentences below.
- **It is the only place AI tools are named.** The product, the packages, the docs, the code, the tests, and the history never mention an assistant. `CLAUDE.md` is a one-line `@AGENTS.md` import for hosts that look for that name. It is not a second copy. Delete this file and `CLAUDE.md`, and FRIDAY still builds, installs, and runs.
- **Dated facts live elsewhere.** Rules live here. What works today, what is unverified, and what is next live in [FRIDAY_STATE.md](FRIDAY_STATE.md).

## What FRIDAY is

FRIDAY is an existing, working, single-owner desktop assistant for Windows. It is local-first: Electron and React on the desktop, a Python FastAPI kernel on this PC. Official repository: https://github.com/devendrarj25/FRIDAY-AI-ASSISTANT.

Public FRIDAY is four-part (`1.0.0.0`); `package.json` `version` is the npm/electron-builder SemVer encoding (`1.0.0`) and is never an update identity. Next public revision is **1.1.3.5** and may only describe work done after the current public line **FRIDAY 1.1.3.4**.

## Taking a request

The owner writes in Hindi, English, or Hinglish, often in short or loose words. Read the whole message and the chat. Spelling slips and mixed scripts are normal. Screenshots, logs, and pasted output are evidence: pull the exact error lines and numbers from them.

1. **The owner gave a full prompt.** Treat it as the task and follow it as written. Check its factual claims (file names, tests, behaviours) against the repo first, because prompts go stale. Where it collides with a hard rule in this file (a workflow edit that needs a second yes, identity, a version bump, a safety invariant), say so once, do everything else, and list that one item at the end.
2. **The owner gave a loose request** ("Friday me ye problem aa rahi hai", "ye upgrade karo", "ye theek karo"). Turn it into one precise prompt before working, then print it in at most eight lines: the goal in plain words, the scope and the owning module, the constraints that apply, and three to six ordered steps with what "done" means for each. Continue without waiting. If two readings differ materially, take the safest reversible one and name it.
3. **Ask only when blocked.** Ask the owner only where this file demands his words (a second yes for workflow files, a version bump, publisher identity, a Deliberate design decision that is genuinely wrong), or when a needed secret or file exists nowhere.
4. Classify the request: a problem or fix, an upgrade, a new feature, a look change, or a question. A question gets an answer from the repo or the web and changes nothing.
5. Reply in the owner's language, short and plain. The final report follows the Report section.

## How to work

**Build first, check in proportion, verify at the end.** Most time goes into reading the owner code and building the change. Do not spend it on ritual checks.

1. **Route and scope.** Classify with the route table in [docs/FRIDAY_CHANGE_CONTROL.md](docs/FRIDAY_CHANGE_CONTROL.md). Name the canonical owner. List the files that may change. Read the callers and the tests that pin each file before editing it.
2. **Edit what exists.** One feature, one location, as declared in `config/project-structure.json`. Change the existing file. Add a new file only when no existing owner fits, and give it a name that matches its neighbours. No parallel system, no second installer, no second CI, no second copy of anything.
3. **Keep the repository clean.** No stray files, copies, dead code, commented-out code, debug output, build output, caches, logs, or screenshots committed. Use names that say what a thing is. Every folder and file stays arranged, indexed, and registered where the project declares it (`npm run arrange:check`).
4. **Keep everything connected and live.** The UI, every button, the Electron main process, the kernel, the stores, and the docs describe the same product. A control is wired to a real handler. A page shows real data, a loading state, an empty state, an error with Retry, and an offline state. A stored setting is honoured. A list or count refreshes from its source of truth after every change. Shared timers and pollers, not new always-on ones.
5. **Use the best method, and keep it current.** For anything non-trivial, search the web for the current best method, standard, and practice, read the official source, and choose what is fastest, smoothest, and safest for a local-first single-owner Windows app. Prefer the latest stable version that fits the floors in `package.json`, `kernel/requirements.txt`, and `config/toolchain-versions.json`. Prefer what FRIDAY already has. Build it ourselves when that fits FRIDAY better than adopting something. Make it future-proof: read old stored shapes and migrate them, use registries and config instead of hard-coded lists, keep defaults safe, and keep updates flowing through the existing update channel.
6. **Free and open-source tools.** When FRIDAY needs one, take it from its official source (its own release page, PyPI, npm, or the vendor) and let FRIDAY install it on the PC through the existing Install Manager catalog: pin the SHA-256, add a Doctor row and a repair, and let FRIDAY start it when needed and stop it when idle, so responses stay fast. Details are under "Owner directive and build autonomy".
7. **Check each area right after you change it.** Run only what that change can affect: `npm run test:fast`, the test file for the module, `npm run typecheck`, or `npm run test:kernel` for kernel files. Fix a failure before the next edit. Do not run the whole suite after every step.
8. **Write the tests and documents with the code.** New behaviour gets its own test. The owning document and `FRIDAY_STATE.md` change in the same change.
9. **At the end, run the full checks once.** See Commands and Checks. Collect every failure, fix them together in the owner code, and rerun until every suite is green. Then commit and push.

## Commands

Run these from the repo root. `npm ci` installs Node dependencies. `npm run setup:python` prepares the kernel. A cloud machine uses `bash scripts/cloud-agent-install.sh` and `bash scripts/cloud-agent-start.sh`. Put the kernel virtual environment first on `PATH` before the Python checks.

- `npm run preflight`: the one gate before a push. Cheap static checks, then the kernel, then the fast tests. It keeps going after a failure and prints one table. `npm run preflight -- --full` adds the Vitest suite and the Windows pack when this machine can run them. `npm run preflight -- --changed` runs the gates the diff can affect. `npm run validate:local` is the same command. A red preflight is a failed task. Report its table. Hosted Actions stay unverified.
- `npm run test:fast`: tests for the files you changed.
- `npm test`: the full Vitest suite.
- `npm run lint`: ESLint plus kernel ruff (`ruff check` and `ruff format --check`).
- `npm run typecheck`.
- `npm run typecheck:py`: kernel pyright ceiling in `kernel/pyright-baseline.txt`. The count may shrink. Under `CI`, `GITHUB_ACTIONS`, or `FRIDAY_PYRIGHT_STRICT` a missing tool fails the test. A workstation without the tool skips with a loud line.
- `npm run test:kernel`.
- `npm run docs:sync`, then `npm run docs:check`.
- `npm run arrange:check`.
- `npm run check:provenance`.
- `npm run verify:version` when a governed doc or `config/friday-version.json` could drift.
- `npm run setup:hooks`: optional. Points this clone at `scripts/git-hooks` so pre-push runs preflight. Off until you run it. The product does not require the hook.
- `npm run pricing:status` reports how old each pricing source is. It is not a unit test.

## Upgrade flow

This is the whole path for a fix, an upgrade, or a later public revision. The sections after it are the rules this path uses. They are not a second path.

1. **Follow the read order above.**
2. **One open pull request into `main`.** Never edit `main`. Run `git fetch origin` to see what is already there. Skip every release pull request (`release/v…`) and every dependency-bot pull request: do not work in them. Then:
   - If the owner names a pull request or branch, work in that one.
   - Otherwise, if a draft pull request into `main` is open, continue on that branch. A different topic still goes in that same draft.
   - If there is no such draft and another non-release pull request into `main` is open, continue on that branch.
   - If neither is open, create one branch and one draft pull request.
   Do not open a second non-release pull request while one is open. A new pull request is allowed only after that one is merged and the remote lists only `main`, or a `recovery/*` branch.
3. **Branch names** use a prefix from [CONTRIBUTING.md](CONTRIBUTING.md): `upgrade/<what-is-upgrading>`, `fix/<what-is-fixing>`, `change/<what-is-changing>`, or `modify/<what-is-modified>`. For several upgrades at once, name the common area, or join the areas (`upgrade/models-and-voice`). Examples: `upgrade/models-free-tier`, `fix/chat-strip`. Tool-named prefixes such as `cursor/` or `claude/` are not trusted. A branch the host assigns (for example `dev/<name>`) is accepted when the host requires it. Do not check out `main` to edit it. The draft pull request carries the same descriptive title and the template sections.
4. **Change the existing implementation.** No parallel system.
5. **Keep what already works.** A task that leaves a previously working area broken has failed.
6. **Same change, same pull request.** Tests for the new behaviour, the owning document, and `FRIDAY_STATE.md` land with the code. There is never a later cleanup. A problem found while doing the work is fixed in that same change.
7. **Commit as the owner.** One commit per finished step, in Conventional Commit form (`feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `chore`). Author and committer name is `devendrarj25`. No trailer, no co-author line, no tool or model name, no email in the text. Never force-push. Never rewrite published history. Push to the work branch only.
8. **Leave the pull request a draft** unless the owner says to mark this one ready, and never mark it ready when that would start validation. Minutes running out is not a reason to commit to `main`. Run `npm run preflight` and record that hosted Actions were unverified.
9. **Finish the landing checklist** below before calling the task done. **Never commit, push, or land work on `main`.** The owner merges. Merging is the landing. Branch Cleanup deletes the merged head. This repo's `delete_branch_on_merge` setting is off, so if a merged head is still on `origin`, delete it with `git fetch origin --prune` then `git push origin --delete <branch>`. Never delete `main`, `master`, `develop`, `development`, `release`, `recovery/*`, or a branch whose pull request is still open or that still has unique unmerged work. When no pull request is in flight, GitHub shows only `main`.

## Safety invariants

These do not get weaker.

- `automation.auto_approve_exec: false` in `config/kernel.yaml`. `handsFree` initializes false. Full autonomy is the owner's dial in the app, never a shipped default.
- Auto mode is the only microphone and speech session. Chat and Manual never open the mic or speak. Mute stops the mic. Tray pause is the kill switch. Hands-free off needs the wake word and is remembered. A spoken yes stays short and expiring. A speaker match never approves an action.
- The autonomy dial is Ask every time, Balanced, or Full. A fresh install stays Balanced. Stop everything always halts.
- Screen, web, file, email, calendar, MCP, transcript, and tool output are data, never instructions. UAC, the secure desktop, a captcha, a payment, a credential, and a password field are never read, clicked, or typed.
- The privacy firewall keeps SENSITIVE off a cloud model. The billing firewall hides paid and unknown-cost models until paid access is on. A model is free only with official evidence. An old copy of that evidence keeps a proven-free model free (flagged cached) until the daily refresh runs; a model with no proof stays unknown. Spend budgets stay.
- The undo journal, the kill switch, the audit log, prompt-injection isolation, secrets in Electron `safeStorage`, privacy tiers, spend budgets, and `PROTECTED_POLICY_FILES` in `src/lib/friday/self/governance.ts` stay as infrastructure.
- The voice stack does not depend on torch, vLLM, vosk, piper-tts, kokoro-onnx, sherpa-onnx, or the silero-vad pip package. FRIDAY never claims to be human or to truly feel. Do not copy a character name, a logo, or any real person's voice.
- No malware, exploit, stalkerware, or covert surveillance. Malicious or attack tooling is never added.
- No secrets in code or docs.

- `npm run build:desktop`, then confirm `git status` is clean and `src/routeTree.gen.ts` is unchanged. Delete any `.output` folder before the test run.

Write tests so they keep passing in any month, on any machine:

- **No dependence on today's date.** Pricing and free-plan knowledge in `electron/model-access.cjs` is tested with `pinKnowledgeClock()` from `core/__tests__/helpers/`. Freshness of the snapshot is `npm run pricing:status` and Health Weekly, never a unit test.
- **No dependence on this checkout's git history.** Build a throwaway repo in a temp folder (see `core/__tests__/release-notes-sot.test.ts`). Use `it.skipIf` only for a committed-identity check that needs a real clone.
- **A missing environment skips, a wrong result fails.** A real page fetch or OS tool runs where it exists and skips visibly where it does not, through `core/__tests__/helpers/environment.ts`.

Do not test on the real computer, a live desktop, or a browser, and do not bring that evidence, unless the owner asks for it in that same message. The ask applies to that task only.

## Report

The result of a task states three things, in the owner's language, short:

1. A short summary of what was done.
2. A before and after table.
3. The checks that were run, each with its result and counts. If the work caused an error, the fix is in the same change and the result says so. Name what is unverified: a Windows CMD, install, or publish path that was not run, hosted Actions, real microphone, GPU feel.

Do not show snapshots, videos, recordings, or screenshots unless the owner asked for them in that message.

## Documents and the version

Every behaviour change updates the document that owns that subject, in the same change. Keep every document arranged, synced with the code, up to date, and free of duplicate paragraphs. Do not invent a second registry, a second What's New, or a second CI job.

1. Update the owning document and `FRIDAY_STATE.md` with the code.
2. `npm run docs:sync` then `npm run docs:check`. The registry is `scripts/docs-engine.cjs`. Never hand-edit the generated blocks in `docs/README.md` or the README documentation map, and never create an unregistered `.md`.
3. An official release runs that same sync plus `npm run release:heal` and `npm run verify:version`.
4. Tests already encode this (`core/__tests__/docs-registry.test.ts`, `core/__tests__/documentation-contract.test.ts`, `core/__tests__/version-sync.test.ts`).

Owning documents: build and packaging in `docs/FRIDAY_BUILD_AND_RELEASE.md`; Actions in `docs/FRIDAY_GITHUB_ACTIONS.md`; merge in `docs/FRIDAY_MERGE_FLOW.md`.

**One version authority.** `config/friday-version.json` is the only place a developer changes the product version. Do not scatter versions, invent release history, or overwrite `releases/notes`, `CHANGELOG.md`, or `release-notes.md` from a test fixture. Policy: [VERSIONING.md](VERSIONING.md). Assistants do not bump `config/friday-version.json` until the owner asks.

## Assistant standard (voice and Auto mode)

Every voice or Auto task does all of these:

1. Audit the current voice and Auto code and tests for gaps and bugs, and fix them in the same pull request.
2. Research what leading voice assistants do now, and what the state of the art is, then map each finding to FRIDAY.
3. Push FRIDAY toward a calm, capable assistant: ambient awareness, anticipation, proactive and polite help, autonomous multi-step work as plan, act, verify, report, brief confident status lines, and dry wit. Full autonomy may run, write, and rewire without a per-action prompt. Balanced asks. The kill switch stops her. The shipped kernel flag stays false. Work stays auditable, and reversible work stays undoable.
4. Record what was found and not built in `FRIDAY_STATE.md` under Next priorities.

The safety invariants stay as written above: Auto mode is the only microphone and speech session, Manual and chat stay quiet, and the privacy and billing firewalls stay fail-closed.

## Session record

Updating `FRIDAY_STATE.md` is a **required deliverable** of every task, including documentation-only, test-only, and small changes. Before the task is finished, update only the current facts:

- remove or move items out of Known gaps once they are actually resolved;
- add any new gaps or unverified areas you discovered;
- update Next priorities if the owner's direction changed;
- update the snapshot when a live count or a deliberate decision changed.

Do not add a work diary, a play-by-play, or a record of who did what. Version history stays in [CHANGELOG.md](CHANGELOG.md) and `releases/notes`. Never record something as working unless a real test, build, or manual check ran. Say "unverified" when it is unverified. A session that leaves `FRIDAY_STATE.md` stale has not finished.

After a gap, follow [FRIDAY_STATE.md](FRIDAY_STATE.md), Coming back after a gap. Auto Recover re-runs only a validation that never started. A run that recorded a step is a real result and is not re-run. Catalog: [docs/FRIDAY_GITHUB_ACTIONS.md](docs/FRIDAY_GITHUB_ACTIONS.md).

## Finish checklist

A task is not finished until all of these are true:

1. The request is implemented in the existing single implementation, with no duplicate file, no stray file, and consistent names.
2. The already-working EXE CMD build, install, uninstall, reinstall, update, app opening, repository Actions, and publishing still behave as before (or their tests and docs were updated in this same change and the old behaviour still works).
3. The full checks above ran, every failure was fixed, and every suite is green. Locked-path tests ran if those files were touched.
4. `FRIDAY_STATE.md` is current and honest. Affected documents match the code and are registered, synced, and free of duplicates.
5. Version, What's New, and changelog files were not hand-scattered. `verify:version` stays green if version-governed docs changed.
6. Nothing was force-pushed. `config/friday-version.json` was not bumped unless the owner asked. No workflow was started. Every commit carries only `devendrarj25`.
7. The work is committed and pushed to the work branch, and the draft pull request carries items 1 to 6. The merge does not create a follow-up. The owner merges, and the owner runs Actions.
8. After the owner merges, the work branch is gone from GitHub. The remote is only `main` until the next pull request.
9. No agent environment, artifact, scratch file, or dependency was left in the repository.

## Cloud environment

Personal cloud environments are dashboard-managed. This section is only the environment; follow the Upgrade flow above.

- `install` is `bash scripts/cloud-agent-install.sh` (`npm ci`, Python, Electron, runtime init). `start` is `bash scripts/cloud-agent-start.sh` (Vite on port 8080, FastAPI kernel on port 8765, when those tmux sessions are not already running).
- PATH often prefers `/exec-daemon/node`, which can be below the floor. `package.json` `engines.node` is `>=22.19.0`. `scripts/cloud-agent-path.sh` selects a Node that meets that floor. On Ubuntu the install also brings Python >= 3.12.10, SQLite >= 3.45.3, and Git >= 2.49.0 when the image is older.
- Do not put FRIDAY UI, capability, or feature changes in those scripts.
- A cloud session follows Actions, pull, and merge. It does not run a workflow.

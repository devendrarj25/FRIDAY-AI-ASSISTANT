# AGENTS.md — instructions for AI tools working on FRIDAY

## What FRIDAY is

FRIDAY is an existing, working, single-owner desktop assistant for Windows.
It is local-first: Electron and React on the desktop, a Python FastAPI kernel
on this PC. Official repository:
https://github.com/devendrarj25/FRIDAY-AI-ASSISTANT.

FRIDAY belongs to **Devendra Singh Meena** (`devendrarj25`). He is the only
recorded owner and the only recorded changer. That GitHub username is the
public identity on every package and on every contribution record. The app
installs, builds, and runs from this repository. **AI assistance is permitted.
AI ownership is not.** Assistants may
write, refactor, test, and document this project. They must never claim
ownership, change the publisher, add their branding or "generated by" marks,
add builder-specific packages, plugins, telemetry, or hosted endpoints,
replace official URLs, or make themselves a required runtime or build service.

## Upgrade flow

This is the whole path for a fix, an upgrade, or a later public revision.
The sections after it are the rules that path uses. They are not a second path.

1. **Follow the read order above.** The "Deliberate design decisions" section
   in [FRIDAY_STATE.md](FRIDAY_STATE.md) is binding. Never silently revert,
   "fix", or override one. If one is genuinely wrong, stop and ask the owner.
2. **One open pull request into `main`.** Never edit `main`. Fetch
   `origin/main` to see what is already there. Skip every release pull
   request (`release/v…`). Then:
   - If a draft pull request into `main` is open, continue on that branch.
     A different topic still goes in that same draft.
   - If there is no such draft, and another pull request into `main` is
     open, continue on that branch. A different topic still goes in that
     same pull request.
   - If neither is open, create one branch and one draft pull request.
   Do not open a second non-release pull request while one is open. Do not
   merge a pull request. The owner merges. A new pull request is allowed
   only after that one is merged and the remote lists only `main`, or a
   `recovery/*` branch. A new branch uses a prefix from
   [CONTRIBUTING.md](CONTRIBUTING.md): `upgrade/<area>-<purpose>`,
   `fix/<area>-<purpose>`, `change/<area>-<purpose>`, or
   `modify/<area>-<purpose>`. Examples: `upgrade/models-free-tier`,
   `fix/chat-strip`. Tool-named prefixes such as `cursor/` or `claude/`
   are not trusted. That rule is the prefix table in CONTRIBUTING.md.
   A host may add its own suffix. Do not hard-code a suffix from an older
   session. Do not check out `main` to edit it. All work stays on the pull
   request branch.
3. **Change the existing implementation.** One feature, one location, as
   declared in `config/project-structure.json`. No parallel system, no second
   installer, no second CI. Touch only the files this task needs. Flag unrelated
   issues instead of editing them.
4. **Keep what already works.** Follow "What must keep working" below. A task
   that leaves a previously working area broken has failed.
5. **Same change, same pull request.** Tests for the new behaviour, the owning
   document, and `FRIDAY_STATE.md` land with the code. There is never a later cleanup.
   A problem found while doing the work is fixed in that same change. Do not
   leave a known break for another pull request.
6. **Check in proportion.** Run the checks under "Checks". Say "unverified"
   when a Windows CMD, install, or publish path was not actually run.
7. **Leave the pull request a draft.** Assistants must **not dispatch** PR
   Validation, Test EXE Build, Official Publish, Release / Build, or any other
   workflow, and must not mark the draft ready or merge it. The owner merges.
   Marking ready is only when the owner says to do that for *this* pull
   request. A draft starts only the
   secret scan. The owner marks it ready; that is the one full validation.
   Minutes running out is not a reason to commit to `main`. Run
   `npm run validate:local` and record that hosted Actions were unverified.
   If validation fails, fix the same branch and leave the pull request for the owner.
8. **Finish the landing checklist** below before calling the task done.
   **Never commit, push, or land work on `main`.** The owner merges. Merging
   is the landing. Branch Cleanup deletes the merged head. This repo's
   `delete_branch_on_merge` setting is off, so if a merged head is still on
   `origin`, delete it with `git fetch origin --prune` then
   `git push origin --delete <branch>`. Never delete `main`, `master`,
   `develop`, `development`, `release`, `recovery/*`, or a branch whose pull
   request is still open or that still has unique unmerged work. When no pull
   request is in flight, GitHub shows **only `main`**.

The working path after the map is
`FRIDAY-DEVELOPMENT & VISION/FRIDAY-DEVELOPMENT/10_DEVELOPMENT_WORKFLOW/FAST_SAFE_CHANGE_WORKFLOW.md`
and `FRIDAY-DEVELOPMENT & VISION/FRIDAY-DEVELOPMENT/14_TEMPLATES/TASK_PACKET_TEMPLATE.md`.
If that folder is removed, nothing in the application, build, or runtime breaks.

## Research-led upgrades

Use this when the work is an upgrade. A bug fix stays the smallest change
that keeps today's behaviour.

1. Open only the related files under `FRIDAY-DEVELOPMENT & VISION`. Take the
   task and the ideas from those files. Route with
   `FRIDAY-DEVELOPMENT/01_SOURCE_ROUTING/` when the area is not already named.
2. Mark every plan requirement DONE, PARTIAL, or MISSING against the code
   and the tests.
3. Do a current web search on the methods, tools, standards, security and
   privacy practice, and comparable products. Use the best method that fits
   FRIDAY. Take the upgrade as far as the plan, the research, and these rules
   allow, in one draft pull request, in phases that are green before the next
   phase starts. A fix, and any file the upgrade does not need, stays the
   smallest change.
4. Keep a finding only when it fits FRIDAY: local-first, single-owner,
   Windows, the privacy and billing firewalls, no assistant-owned dependency,
   no second implementation, and testable without hardware, network, or
   today's date.
5. Implement in the existing product path. One feature, one location.
6. When that behaviour is in FRIDAY and its tests pass, remove the entries
   that were implemented. When a file has no entries left, delete that file.
   When a folder has no files left, delete that folder. Update every index
   and link that named them in the same change, so the remaining paths still
   resolve. Do not delete a file that still has behaviour missing from the
   product. Do not delete product docs under `docs/` or the repo root.
   `AGENTS.md`, `AUDIT.md`, and `FRIDAY_STATE.md` stay at the repo root.

Record the research once, in the owning product document: the date, the
source links, and ADOPT, ADAPT, or REJECT with one reason. Do not quote
sources at length, do not add a research document, and do not present a
memory as a current source. If the web is unavailable, write unverified and
do not invent a source.

A new product dependency is recorded once in the owning document: source,
date, ADOPT, ADAPT, or REJECT, one reason, bundled or installed, and size.
Install it as stated under Owner directive and build autonomy.
A copyleft (GPL or LGPL) voice component stays optional, downloaded on demand
from the official upstream onto the owner's PC, never committed and never
bundled into the EXE, and run as a separate process or optional import so
FRIDAY works without it.

Anything found and not built goes in `FRIDAY_STATE.md` under Next priorities.
Do not open a second vision document.

### Changing something that already works

Later fixes and upgrades will touch code that is already correct. Do it this way:

1. Keep the old behaviour working (same CMD build, same install / uninstall
   / reinstall / update, same Actions triggers and guarantees). The look
   of the app stays, as stated above. New controls use the existing tokens
   and components.
2. Update the tests that already encode that behaviour in this same landing.
   Add a targeted test only when a real contract is missing. Never delete,
   skip, disable, weaken, or fake-pass the old contract.
3. Update the owning document and `FRIDAY_STATE.md` in this same landing.
4. Prefer a small, verified step over a rewrite when the task is a fix. An
   owner-requested upgrade follows Research-led upgrades.
5. Run the tests that cover the behaviour you just changed. Fix a failure
   before the next edit. Do not leave a known break for a later commit.

## Owner directive and build autonomy

FRIDAY is the owner's private personal assistant. The owner's instruction for
a task is final. Decide, build, and report. Do not stop a build to ask
permission, and do not leave a list of decisions for later.

Free and open-source tools may be installed from npm, PyPI, or an official
GitHub release. Prefer packages that ship inside the app so the feature works
offline after install. For a binary, download the Windows release, compute
the SHA-256, pin it in the existing Install Manager catalog, and let the app
install it, with a Doctor row and repair. A missing vendor checksum is not a
reason to skip the tool.

Runtime autonomy is the owner's dial: Ask every time, Balanced, or Full
autonomy. A fresh install stays Balanced. Full autonomy runs, writes,
executes, and rewires without a per-action prompt. One switch on Auto mode
and on the Flow Studio toolbar turns it on, and the choice stays on this
machine. Stop everything still halts her.

The undo journal, the kill switch, the audit log, prompt-injection isolation,
local secrets, privacy tiers, and spend budgets stay in place as
infrastructure. A branch and a draft pull request stay the way work lands.
Publisher identity, project independence, and version bumps stay unchanged
unless the owner asks. Malicious or exploit tooling is never added.

## Checks

Do not delete, disable, weaken, or fake-pass tests. New behaviour gets its
own test in the same pull request. PR Validation warns when code changed and
no test did.

Write tests so they keep passing in any month, on any machine:

- **No dependence on today's date.** Pricing / free-plan knowledge in
  `electron/model-access.cjs` is tested with `pinKnowledgeClock()` from
  `core/__tests__/helpers/`. Freshness of the snapshot is `npm run pricing:status`
  and Health Weekly, never a unit test.
- **No dependence on this checkout's git history.** Build a throwaway repo
  in a temp folder (see `release-notes-sot.test.ts`). Use `it.skipIf` only for
  a committed-identity check that needs a real clone.
- **A missing environment skips, a wrong result fails.** A real page fetch or
  OS tool runs where it exists and skips visibly where it does not, through
  `core/__tests__/helpers/environment.ts`.

Run these in the same task, and fix every failure the work caused before the
task is called done:

- `npm test` (includes the locked-path set, the independence regex scan, and
  `core/__tests__/stable-section.test.ts`); `npm run test:fast` while you
  work, for the tests related to the change
- `npm run lint` when any JS or TS file changed, and when the owner asked for
  lint on the task. Fix findings. Do not silence a rule
- `npm run check:provenance` when product text or commits could carry a tool
  mark. That command is the provenance regex scan
- `npm run typecheck` when TypeScript changed
- `npm run docs:sync` and `npm run docs:check` when any Markdown or registry
  document changed
- `npm run verify:version` when version-governed docs or
  `config/friday-version.json` could drift
- `npm run arrange:check` when layout, folders, or ownership changed
- `npm run test:kernel` when any `kernel/` file changed

A document-only edit runs the docs checks, version verify when a governed
doc changed, and the tests that read the changed files. It does not need a
kernel run. Run the full suite when the change is large, crosses subsystems,
touches a locked area, or the owner asks.

Linux-only evidence is not a Windows CMD, install, or publish verification.
Do not claim those are verified unless a `windows-latest` run or the owner's
PC actually ran them.

## Assistant standard (voice and Auto mode)

Every voice or Auto task does all of these:

1. Audit the current voice and Auto code and tests for gaps and bugs, and
   fix them in the same pull request.
2. Research what leading voice assistants do now, and what the state of the
   art is, then map each finding to FRIDAY.
3. Push FRIDAY toward a calm, capable assistant: ambient awareness,
   anticipation, proactive and polite help, autonomous multi-step work as
   plan, act, verify, report, brief confident status lines, and dry wit.
   Full autonomy may run, write, and rewire without a per-action prompt.
   Balanced asks. The kill switch stops her. The shipped kernel flag stays
   false. Work stays auditable, and reversible work stays undoable.
4. Record what was found and not built in `FRIDAY_STATE.md` under Next

session, Manual and chat stay quiet, Mute microphone stops the mic, tray
pause is the kill switch, Hands-free off requires the wake word and is
remembered, the privacy firewall and the billing firewall stay fail-closed,
and a spoken yes stays short and expiring.

7. Items 1–6 are already in the pull request. The merge does not create a

8. After the owner merges, the work branch is gone from GitHub. The remote

## Cloud environment

Personal cloud environments are dashboard-managed. Follow the upgrade
flow above; this section is only the environment.

- `install` is `bash scripts/cloud-agent-install.sh` (`npm ci`, Python, Electron,
  runtime init). `start` is `bash scripts/cloud-agent-start.sh` (Vite on port
  8080, FastAPI kernel on port 8765, when those tmux sessions are not already
  running).
- PATH often prefers `/exec-daemon/node`, which can be below the floor.
  `package.json` `engines.node` is `>=22.19.0`. `scripts/cloud-agent-path.sh`
  selects a Node that meets that floor. On Ubuntu the install also brings
  Python >= 3.12.10, SQLite >= 3.45.3, and Git >= 2.49.0 when the image is older.
- Do not put FRIDAY UI, capability, or feature changes in those scripts.
- Do not dispatch GitHub Actions from a cloud session.

## 1. One pack path

`scripts/build-pipeline.cjs` is the only Windows pack recipe. The CMD wrapper, `npm run build:win`, `build:win:dir`, `build:all`, `release:package`, `build:portable`, `desktop:build`, `desktop:pack`, FRIDAY Release, and FRIDAY Test Build call it. They differ only by named options: channel (`production` or `test`), version stamp, package targets, signing, and whether a later job publishes. The phase order does not change.

The desktop Vite build writes `src/routeTree.gen.ts` with the same Start footer as the web plugin (`scripts/route-tree-footer.cjs`, `routeTreeFileFooter`). A desktop build leaves that committed file unchanged.

`scripts/electron-pack.cjs` passes `--publish never` unless the command already names `--publish`. electron-builder 26 otherwise treats a CI run that is not a pull request as `onTagOrDraft` and stops when `GH_TOKEN` is unset. Official assets are still uploaded by `gh release create`.

File names use the public four-part identity. The npm field stays the three-part encoding. ExtraResources copy the kernel, the capability trees, and the scripts, except the cloud-environment helper scripts. The `resources` extraResource omits `to`: electron-builder resolves that field relative to the app resources directory, and `to: resources` nested the staged packs at `resources/resources`. `verify-artifacts` requires `win-unpacked/resources/<dest>/<id>/pack.bin`. A report is written to `release/build-report.json`.

The first pack needs the network so `scripts/stage-toolchain.cjs` can fetch the packs named in `config/toolchain-manifest.json` and check their SHA-256. Later packs reuse `.cache/toolchain`. `--offline` and `FRIDAY_OFFLINE=1` reuse that cache and fail with `offline build: <id> is not in the staging cache` when a pack is missing. `FRIDAY_SKIP_TOOLCHAIN_STAGE` is refused: a skipped stage must not emit a small EXE. Setup and Portable must be at least 70 percent of the bundled pin sum and strictly under 2 GiB (and under the manifest budget plus 800 MiB). A missing pack or a short installer fails the build with the text `refusing a small EXE`. `packaged-self-check` is a pipeline phase. A Linux run skips it with `skipped: packaged self-check runs on Windows only`. A Windows run of that phase, the CMD pack, and installer smoke is unverified until `windows-latest` or the owner's PC runs them.

## 🪪 Package identity

Every package kind reads `scripts/identity.cjs`. The kinds are npm (`package.json`), the NSIS Setup, the portable EXE, the unpacked app, the source zip (`FRIDAY-PACKAGE.json`), and the update manifest (`friday-update.json`). The stamp is the product name **FRIDAY**, the owner **Devendra Singh Meena**, and the GitHub username `devendrarj25`. The publisher line is `Devendra Singh Meena (devendrarj25)`. Those records do not carry an email, a phone number, or a street address.

An installed copy keeps `scripts/identity.cjs` beside the app, under `resources/scripts`. `electron-builder.yml` ships the scripts tree as an extra resource and packs only `scripts/release-engine.cjs` inside `app.asar`. `electron/dev-workflow.cjs` loads the checkout path when that file is present, then `resources/scripts/identity.cjs`. The installed main process reaches the boot self-test after that load succeeds. That check mounts the window and exits on its own clock. It does not extract Python and it does not start the kernel. A normal launch still does both. Installer smoke passes `--friday-boot-selftest` and `--friday-workspace` because a redirected GUI process can miss the inherited environment. A renderer crash during the check exits with `FRIDAY_BOOT_SELFTEST_FAIL` instead of reloading until the 240 second kill. The same process replaces `<root>\logs\boot-selftest.txt` (BEGIN, then OK or FAIL). Smoke accepts that file as well as stdout, and it deletes the file before each launch so an older OK cannot pass the next boot. A normal second launch still quits. The boot self-test does not take the single-instance lock.

### Boot self-test and readiness (packaged app)

Both checks launch the packed EXE with the software compositor, on their own clock, and report through files, never a redirected stdout (a Windows GUI process does not deliver stdout to a redirected pipe).

- **Boot self-test** (`--friday-boot-selftest`, `--friday-workspace`): `electron/main.cjs` returns into `electron/boot-selftest.cjs` before the workspace, kernel, and Python requires. That file registers the `friday://` scheme, answers `workspace:get` with the sandbox folder, mounts the real renderer, and exits. It replaces `<root>\logs\boot-selftest.txt` (BEGIN, then OK or FAIL), does not take the single-instance lock, and never extracts Python or starts the kernel. A renderer crash exits with `FRIDAY_BOOT_SELFTEST_FAIL`. Smoke deletes the file before each launch so an old OK cannot pass; a normal second launch still quits. `scripts/verify-boot.cjs` and installer smoke read the same file.
- **Readiness** (`--friday-readiness`, `--friday-workspace`, `--friday-python`, `--friday-progress`): stages START, ROOT, BOOT, KERNEL, DATABASE, MODEL, CHAT, VOICE, BASIC TASK, then SHUTDOWN and RESTART. It writes `logs/readiness-progress.jsonl` (timestamp, milestone, milliseconds) and `logs/readiness-result.json`. A per-milestone watchdog writes the result and exits; the ceiling is 5 minutes while milestones advance, and 30 seconds when a `load:` milestone stops or the process exits. No stdout sink, no tray, catalogue, plugin, or provider probe, no registry or `py` scan, and no bundled-runtime extract. A first launch with no report marks SHUTDOWN and RESTART `not evaluated` and does not start a second wait. Each subsystem require writes `load:<module>` first, so a hang names the module.
- **Startup rules that keep `ready` reachable:** no `app.getPath("userData")` during module load (applied in the ready handler; voiceprint path, sandbox restart file, and bootstrap settings wait for `app.isReady()`); `safeStorage`, `desktopCapturer`, `Tray`, and `nativeImage` are read through `electron/lazy-electron.cjs` only after ready; JSON under `config/` resolves through `electron/resource-paths.cjs` (packaged resources, checkout, asar, `execPath/resources`, and a directory above an extracted `app.asar.unpacked/electron`), cached, with a Doctor warning and a fail-closed fallback when missing. The `uncaughtException` handler registers before those requires. There is no second copy of `config/` inside `app.asar`. `scripts/packaged-requires.cjs` lists the built asar before readiness, and a require that throws writes `load-failed:<name>`.
- **Exit order:** `electron/app-lifecycle.cjs` awaits cleanup and then calls `app.exit` once (never quit then exit in one turn). Sidebar, tray, window close, the approved `app_restart` and `app_shutdown` tools, the installer handoff, window-all-closed, session end, and readiness use it. `/health` carries `instance_id` from `FRIDAY_INSTANCE_ID`, and a launch accepts only the kernel it spawned. `scripts/packaged-launch.cjs` is the one harness that kills the process the boot or readiness parent spawned and checks the pid afterwards.
- **Local reproduction** (from the checkout, after `npm run setup` and a packed `release\win-unpacked\FRIDAY.exe`):

```bat
rmdir /s /q %TEMP%\friday-readiness-clean
node scripts\readiness-test.cjs --pack --no-repair --root %TEMP%\friday-readiness-clean --app release\win-unpacked\FRIDAY.exe
```

A hang prints `hung after <milestone>`; the reports are `debug\reports\readiness-*.json` and `%TEMP%\friday-readiness-clean\logs\readiness-progress.jsonl`. Shutdown from the sidebar does not change start-at-login. A normal double-click keeps the GPU.

`auditPackageIdentity` checks the stamp for all six package kinds, and the identity test runs it on every machine. On Windows, `scripts\build-windows.cmd` reaches the same publisher through `scripts/verify-build.cjs` (product name, company name, file version from the EXE resources). A check on Linux does not replace that Windows resource read.

## 2. Rebuild, update, and auto

Official `mode` means one of these:

- **rebuild** — pack the **same version** again and replace the release assets. `revision` is this same rebuild. The number does not move.
- **update** — move one counter, open the `release/v…` pull request, then publish. The number is used only after that publish succeeds. The same release type retries a failed number. A different explicit level skips that number and counts from the last success.
- **auto**, when `release_type` is also auto — finish the unpublished line as it stands. It does not invent the next number. If you pick patch, minor, major, or extreme yourself, only that one counter moves, even when `mode` is auto, and even when that line has never been published. A stable git tag counts as a published number, the same as a GitHub release.

`scripts/release-engine.cjs` writes the identity into the tree before the pack. The in-app Analyze preview asks that same decision, including a stable git tag, and does not compute a second number. The in-app update check and the release list both read up to 100 GitHub releases, the same window FRIDAY Release uses. An installed copy checks the SHA256 in `friday-update.json` before it replaces itself.

## 3. 🧪 TEST identity

`.github/workflows/test-build.yml` (**FRIDAY Test Build**) packs a Windows EXE from a branch, a tag, a commit, or `pr/<n>`. It does not edit `main`, it does not change `config/friday-version.json`, and it does not create a Latest stable release. It calls `scripts/build-pipeline.cjs --channel test`.

| Property          | Official (`electron-builder.yml`) | TEST override                         |
| ----------------- | --------------------------------- | ------------------------------------- |
| `appId`           | `dev.friday.desk`                 | `dev.friday.desk.test`                |
| `productName`     | `FRIDAY`                          | `FRIDAY Test`                         |
| Setup name        | `FRIDAY-Setup-<ver>.exe`          | `FRIDAY-Test-Setup-<ver>.exe`         |
| Uninstall display | `FRIDAY - Personal AI Assistant`  | `FRIDAY Test - Personal AI Assistant` |

The executable file name stays `FRIDAY.exe`. The separate app id is what lets Windows keep TEST beside Official.

`electron/build-channel.cjs` reads the channel in this order: `FRIDAY_BUILD_CHANNEL` or `FRIDAY_TEST_BUILD=1`, then the packaged `resources/build-channel.json`, then production. The pipeline writes `resources/build-channel.json` with `channel: "test"` before the pack, and deletes that file on a production pack. Test profile data stays apart from the Official FRIDAY folder.

Dispatch inputs:

- `ref` — branch, tag, commit, or `pr/<n>`
- `package` — installer, portable, or unpacked (publish needs an installable artifact)
- `publish` — default false. True uploads a prerelease `v<four-part>-test.N` with `--prerelease`

## 4. 🔄 Stable and Test on an installed copy

Settings → Updates → Update channel. The choice is stored in `<FRIDAY_ROOT>/config/github.json` as `updateChannel` (`electron/github-sync.cjs`). `normalizeUpdateChannel()` maps anything else to `"stable"`.

| Channel           | What it offers                                                               | Windows identity       |
| ----------------- | ---------------------------------------------------------------------------- | ---------------------- |
| Stable (default)  | Releases with `isPrerelease: false`                                          | `dev.friday.desk`      |
| Test (you opt in) | Prereleases, and names that match test, rc, beta, alpha, nightly, or preview | `dev.friday.desk.test` |

Each channel remembers its own applied build: `appliedRef` for Stable, `testAppliedRef` for Test.

A packaged copy uses GitHub Releases only (`checkUpdate` in `electron/github-sync.cjs`). `electron/updater.cjs` is not a second app feed. The file that installs is an installer. It is checked with the SHA256 in `friday-update.json`, then `electron/update-safety.cjs` takes a backup, installs, checks health, and rolls back if that check fails.

An unpackaged checkout may use `channel: "branch"` against HEAD. That mode is not available once the app is packed.

Candidates are ordered by `compareBuilds` in `scripts/release-engine.cjs` (four-part, then `-test.N`). Official publish cleanup keeps the newest 3 stable releases. Maintenance Cleanup keeps the newest TEST prerelease. Those cleanup rules are in [FRIDAY_MERGE_FLOW.md](FRIDAY_MERGE_FLOW.md).

## 5. 🔏 Signing

Unsigned is the honest default (`signExecutable: false`). The pipeline signs only when `CSC_LINK`, `WIN_CSC_LINK`, or `FRIDAY_PFX` is set, and it does not print the password. On FRIDAY Release and FRIDAY Test Build the same repository secrets are optional: `WINDOWS_SIGNING_CERTIFICATE_BASE64`, `WINDOWS_SIGNING_CERTIFICATE_PASSWORD`, and the variable `WINDOWS_SIGNING_PUBLISHER`. The password is the PowerShell step environment (`CERTIFICATE_PASSWORD` copied to `CSC_KEY_PASSWORD`), not written to `GITHUB_ENV`, so a Windows PowerShell 5.1 UTF-8 BOM cannot corrupt it. The PFX file is deleted after the pipeline returns.

To enable signing, store the base64 `.pfx` and its password as those secrets, and set `WINDOWS_SIGNING_PUBLISHER` to the certificate subject the smoke should expect. A run without the secrets stays unsigned and says so.

Since 2024 an EV certificate and Azure Trusted Signing do not skip SmartScreen reputation. An unsigned build, and a newly signed build, show "unknown publisher" until download reputation builds. There is no manual SmartScreen submission for consumer endpoints. Optional Authenticode is also described in [SECURITY.md](../SECURITY.md).

## 6. Pipeline details

The CMD pack, `npm run build:all`, `npm run release:package`, `npm run build:portable`, FRIDAY Release, and FRIDAY Test Build call `scripts/build-pipeline.cjs`. Change a phase there and every entry point follows. Named differences are the channel file, the version stamp, the tag namespace, retention, the signing source, and whether a later job publishes. `scripts/build-windows.cmd` is `node scripts\build-pipeline.cjs --channel production --caller cmd` and returns that process's exit code. FRIDAY Release and FRIDAY Test Build pass `--channel` and `--caller`, then `--through verify-versions` and `--from stage-toolchain`. They do not list the phases themselves.

Phases, in order: prepare-environment, verify-versions, stage-toolchain, build-renderer, package, packaged-requires, sign-hook, manifest, verify-artifacts, verify-boot, readiness, packaged-self-check, installer-smoke.

The installer floor is 70 percent of the bundled pin sum (205118234 bytes), which is 143582763 bytes. The ceiling is under 2147483648. A missing pack or a file under that floor fails the build. The pinned get-pip script (commit-pinned in pypa/get-pip, https://raw.githubusercontent.com/pypa/get-pip/fa4e90301bf000c36309f3ad79c3ac720b55d6df/public/get-pip.py, 2234489 bytes, SHA-256 `f4448a01e3ab2914c65f4ca59d4cacba6b2dbde19a483fbac46587f8bbaff424`) is hash-checked before it runs. The rolling `bootstrap.pypa.io/get-pip.py` URL changes with every pip release, so a hash pinned to it fails the build (PR Validation `package-windows`, 2026-11-03: `checksum mismatch`); a commit URL never changes. The pin is commit `fa4e903` (pip 26.2.2), not the newest: get-pip from 2026-10-29 runs the bundled pip as a subprocess named `pip`, and pip's Windows guard then stops with `To modify pip, please run ... -m pip`, which failed `packaged-self-check` on 2026-11-03. The app downloader (`electron/model-download.cjs`, also used by `scripts/stage-toolchain.cjs`) asks for `Accept-Encoding: identity`, because `raw.githubusercontent.com` gzips text files and reports the compressed `Content-Length`, which cut the file short and failed the checksum.

The first toolchain stage needs network. After that, the cache is `.cache/toolchain/<sha256>.bin`. `--offline` and `FRIDAY_OFFLINE=1` reuse that cache. A miss fails with `offline build: <id> is not in the staging cache` and does not fetch. The CMD wrapper forwards extra arguments, so `build-windows.cmd --offline` is the same flag.

`packaged-self-check` checks each staged pack hash and size, extracts Python, whisper.cpp, and Node with the pure-Node extractor, flattens the Node zip when it has one top folder, and copies ggml-base. The embeddable zip has no pip. The check writes `python312._pth` through `embedPthText`, copies the pinned get-pip script, runs `python.exe get-pip.py`, then `python -m pip --version`, the sandbox probe, `whisper-cli -h`, the MCP launcher, `node.exe --version`, and a 16-byte model header that must not be a zip. On a build machine the launcher reports that FRIDAY is not running, and that answer passes. Output that contains `initialize` also passes. On anything other than Windows the phase returns `skipped: packaged self-check runs on Windows only`. A missing unpack or a failed probe fails the build, and the probe output is in the error. The detail is in `release/build-report.json`.

Installer smoke is `scripts/windows-installer-smoke.ps1` for both channels. The pipeline still passes `-Installer`, `-Product`, and `-ReleaseDir`. With no `-Installer`, the script looks for `release\FRIDAY-Setup-<public version>.exe` from `config/friday-version.json` and names that path if the file is missing. The sandbox is `RUNNER_TEMP` when GitHub sets it, otherwise the system temp directory. A null path is not passed to `Join-Path`. It installs silent per-user into that temp folder, boots, checks kernel health, the update-manifest sha512, orphans (kernel, whisper, browser, MCP launcher), the chosen data folder, then uninstalls, and the `finally` block removes the sandbox. It does not delete the owner's `<FRIDAY_ROOT>`. POSIX skips that phase with an explicit message.

## 7. Models fetched during setup

On Windows, `npm run setup` (`scripts/setup-python.cjs`) runs `scripts/prefetch-models.cjs` after the voice packages import. The Ollama and llama.cpp installers it downloads are pinned with a SHA-256 in `config/local-runners.json` (Ollama v0.40.15, llama.cpp b12230 as of 2026-11-09); `npm run runners:status`, also the last Doctor step, says when a newer official release exists, and a bump means downloading that release once and recording its size and SHA-256. The installer's `repair-runtime.ps1` also checks that the installed runtime imports faster-whisper, PyAV and edge-tts (it installs `kernel/requirements.txt` when they are missing and records `voice-packages-failed` if they still are), and `verify-build.cjs` fails a package without the wake model or the speech, voice and wake kernel files. It fetches faster-whisper base and small (Systran; the two light sizes for live talk, base first so listening starts at once) and, on a PC with at least 8 GB RAM, the larger `medium` for long or hard speech (chosen in Settings, Voice, Speech size; `FRIDAY_PREFETCH_STT_LARGE=0` skips it), the pinned Smart Turn and Silero VAD ONNX files, and, where Ollama does not provide the same small model, the Qwen2.5 1.5B Instruct GGUF from Qwen's own repository into the selected FRIDAY folder (`cache/stt/<size>` and `models/`). It goes through `electron/model-download.cjs`, the same downloader the app uses: allowlisted hosts, a SHA-256 check against the pinned digest or the Hugging Face listing read with `blobs=true`, and, before that engine, the official Hugging Face client (`electron/hf-hub-download.cjs`: `huggingface_hub` with `hf_xet`, `HF_XET_HIGH_PERFORMANCE=1`, progress read from the folder and its `.incomplete` parts, every file checked against the listed size and SHA-256, cut off after 60 seconds without growth, then the chunk-queue engine below as fallback; `FRIDAY_HF_ENGINE=own|hub|auto`), because a plain resolve link for a Xet-backed file goes through Hugging Face's LFS bridge for older clients; research 2026-10-25, sources: Hugging Face's Xet and storage-backend documentation and blog (huggingface.co/docs/hub/en/storage-backends, /docs/hub/en/models-downloading, /blog/xet-on-the-hub), ADOPT because it is Hugging Face's own documented fast path and already installed, REJECT as a hard dependency because it could not be run against Hugging Face here and a forum report names slower results on some routes, so it is first with the built-in engine as fallback; the built-in one is a chunk-queue engine: a file over 24 MB is cut into 8 MB chunks (finer when the file is mid-size) that a pool of connections pulls; the pool starts at four, adds two while the measured speed rises by at least 12 percent per step, and stops at sixteen for one file and 24 in all, because one connection to a CDN often stays at 1 to 2 MB/s on a fast line while too many together can be throttled; a connection with no byte for 20 seconds, or a server with no response headers for 20 seconds, ends and its chunk is asked again on the next host of the same publisher; the files of one repo download three at a time and report as one transfer whose total comes from the repo listing, so the percent is right from the first byte; the models themselves download one at a time (`FRIDAY_PREFETCH_PARALLEL`, default 1), which keeps one live progress line (bar, percent, MB of MB, MB/s over the last seconds, ETA, connections), and a log prints one line per ten percent and the average speed when a model is done) in which every range is held to its exact length (a stream that ends early asks again for the rest, and a server that answers a range request with anything but 206 is fetched once as a single clean stream). A stopped download keeps its `.part` together with a `.part.json` table of the bytes each range wrote and resumes from that table only; a partial file without its table is discarded, because a size alone says nothing about holes left by parallel ranges. A file that still fails its SHA-256 is fetched once more cleanly before the error is reported. The offline neural voice (Supertonic 3, `Supertone/supertonic-3`, every file checked against the publisher's digest) is fetched into `<root>\models\supertonic-3` the same way and marked complete with `.friday-complete` only after a whole run (`FRIDAY_PREFETCH_TTS=0` skips it). The opt-in mirror stays behind `FRIDAY_HF_MIRROR=1`. The step runs under a four-hour limit in `scripts/setup-python.cjs` (the earlier one-hour limit ended a slow Ollama download silently). `npm run setup` and `build:win` both run this step, so it is idempotent: a piece already on disk is verified (its pinned SHA-256 where one exists) and skipped without any network call, and `build:win` also skips `npm ci` when `node_modules` is newer than `package.json` and `package-lock.json` and Electron is in place (`FRIDAY_FORCE_NPM_CI=1` forces it). A failed or offline fetch prints `not prefetched ... FRIDAY fetches it on first use` and never fails setup. `FRIDAY_PREFETCH=0` skips all of it and `FRIDAY_PREFETCH_CHAT=0` skips the chat model; hosted CI skips it unless `FRIDAY_PREFETCH=1`. The load probe then opens the downloaded small (or base) folder, and `scripts/verify-deps.cjs` checks the venv setup built. Nothing is added to the installer or the EXE. Supertonic stays on demand because no digest is pinned for it.

Setup and the scripts resolve the FRIDAY folder in the app's order: `FRIDAY_WORKSPACE_ROOT`, then the registry, then the settings pointer. A folder left by `windows-installer-smoke.ps1` or `readiness-test.cjs` (a `friday-installer-smoke-<32 hex>` or `friday-readiness-<6>` folder under a temp directory) is never adopted, by the scripts or by the app. The smoke restores the owner's `friday-settings.json` pointer files when it ends. Readiness hands the packaged EXE the interpreter setup built (`resolveVenvPython()`).

**Toolchain packs.** `scripts/stage-toolchain.cjs` tries each pack's primary URL and then its pinned `mirrors` (python.org then Huawei Cloud and npmmirror for Python and Node; hf-mirror.com only with `FRIDAY_HF_MIRROR=1`). Every candidate must match the pinned SHA-256 and size, so a mirror is only another road to the same bytes; a failed or wrong source logs `trying the next source`. Downloads use the app downloader (`electron/model-download.cjs` `downloadUrl`: range segments, resume inside the run, retries) and print a progress bar with speed and ETA (a redrawn bar on a terminal, a line every 10 percent in a log). Mirror URLs were not reachable from the Linux container that wrote them, so they are unverified until a Windows build uses them.

**Voice speed and setup resilience (2026-11-07, built and unit-tested on Linux; unverified on the Windows PC).** Findings from the owner's setup and build log, all fixed: (1) `prefetch-models.cjs` ended with `process.exit()` while the network layer was closing sockets, which aborts Node on Windows with `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING)`; it now sets `process.exitCode` (with an unref'd 5 s backstop), and Doctor does the same. (2) A DNS or Wi-Fi drop during the model step failed `stt-medium` and the chat model and ended setup with "SETUP FAIL"; the step now runs again up to three more times (15 s, 30 s, 60 s) when every failure looks like the network (`FRIDAY_PREFETCH_RETRIES`, default 3, 0 turns it off), and only gives up for a wrong file (checksum, signature). Nothing else in that folder is touched by a keep uninstall, and no data folder is. These NSIS lines could not be compiled here (no `makensis` on Linux): they are pinned as text by `core/__tests__/clean-install-contract.test.ts`, executed against a real folder tree and a fake registry by `core/__tests__/single-root-install.test.ts`, and unverified until a Windows pack and `windows-installer-smoke.ps1` run them.

**Download sources of the CMD build (checked 2026-11-02).** Every tool in `scripts/setup-windows.ps1` and `electron/toolchain.cjs` is tried in order: winget (or npm, pip, cargo), the vendor release feed with a pinned SHA-256, then Chocolatey and Scoop when they are already on the PC (never installed by FRIDAY). Found stale and fixed: the KoboldCpp pin pointed at a deleted tag (now v1.124.1, kept in one value in `toolchain.cjs` and `config/local-runners.json`, pinned equal by `core/__tests__/download-sources.test.ts`); `Gradle.Gradle` and `Apache.Maven` are not in winget-pkgs, so they now install through Chocolatey or Scoop and the vendor page; winget exit code 0x8A150014 means "no package with this ID" and was wrongly read as success, so it now fails and the next method runs; the Git fallback matches `Git-*-64-bit.exe`. Checked live from a build machine: the GitHub release pins, the npm and PyPI feeds, Node, Rust and the Scoop names. Not reachable from the cloud session, so unverified: python.org, aka.ms, bootstrap.pypa.io, huggingface.co, ollama.com, go.dev and the winget CDN. A Windows run of `scripts\build-windows.cmd` stays unverified until the owner runs it.

**Everything is fetched before the build, and Doctor checks it (`scripts/ensure-electron.cjs`).** The order is `npm run setup` (the Windows toolchain, then the same fetch steps), `npm run doctor` (checks every row of `scripts/check-environment.cjs` and repairs what is missing), then `scripts\build-windows.cmd`, whose first phase runs the same steps again, so a PC that skipped setup is still prepared. One download used to happen only in the middle of packaging: electron-builder fetched NSIS and its plugins (the `nsis-3.0.4.1` and `nsis-resources-3.4.1` assets of the electron-builder-binaries releases on GitHub, each pinned by SHA-256 inside electron-builder; both URLs and both hashes were checked from the cloud session on 2026-11-02), so one dropped connection there failed the whole pack and Doctor could not see it. `ensure-electron.cjs` now fetches them with electron-builder's own downloader into its cache folder (`.cache/electron-builder`, the folder the build uses), retries twice, records what it fetched in `.friday-installer-tools.json`, and Doctor shows an "Installer tools (NSIS)" row that repairs through the same script. The pins are read from the installed electron-builder, so an upgrade of it is followed with no edit here; `ELECTRON_BUILDER_BINARIES_MIRROR` is honoured. Windows only. Covered by `core/__tests__/installer-tools.test.ts` with a fake downloader; the real download on Windows is unverified.

**Update source and install (Settings → Updates).** The Updates section only reads from GitHub. It keeps its own credential, `github.update.token` in the encrypted store, which can be a fine-grained token with Contents: Read-only on one repository; Friday Hub's write token (`github.token`) is separate, and an older install that has only the Hub token keeps updating with it until a read-only token is added (the panel says so). Every update request goes through `updateCfg()` in `electron/github-sync.cjs`, which marks the config read-only; `api()` refuses any non-GET call made with it. Test connection (`github:test`, `testUpdateSource`) reports public or private, which token was used, whether that token is read-only, the newest official and test release and how many files each has. A checked release lists every file with a recognised kind and a one-line purpose (`classifyAsset`: Windows installer, portable app, release manifest, checksums, updater metadata, notes, source archive) plus the full source zip GitHub builds for the tag. Installing an app update downloads the installer, checks its SHA-256 against the manifest, stops the kernel, backs up the protected folders, records the pending update, then starts the installer silently in place with `/S --updated --force-run` through `cmd start /wait`; if the installer fails, the still-installed app is reopened. Data folders (`config`, `security`, `memory`, `conversations`, `brain-data`, `database`, models, voices, downloads and the rest of `MUST_PRESERVE`) are never replaced, and the next launch's health check offers the backup if the new version does not start. The connection is remembered across restarts (address in `config/github.json`, tokens in the encrypted store); `autoCheck` is on by default for a connected repository, FRIDAY reconnects at start, checks once about 15 seconds after launch when the last check is over 30 minutes old, then every `intervalHours`, and pushes "update available" into the notification centre so it reaches the owner with the panel closed; a packaged app only notifies. `api()` sends `If-None-Match` and reuses a 304 (an authenticated 304 is not counted against the rate limit) and reports an exhausted request limit (403/429 with `x-ratelimit-remaining: 0`) as a limit with its reset time, not as a bad token. Every update download (installer, source zip, pack) goes through one downloader, `electron/resilient-download.cjs`: it writes a `.part` file, resumes it with a Range request after a dropped connection, abandons a stream that stops sending for 45 seconds, tries up to six times with a growing pause (honouring Retry-After), does not retry a definite 400/401/403/404/410, follows redirects by hand so the token goes only to GitHub's API and never to the CDN, refuses a web page or a cut-off zip, checks free disk space before writing (a full drive is a plain message, not six retries), reports size, speed and time left four times a second at most, and replaces the destination only after the checksum matches. It runs on the app's own network stack, so a Windows proxy or company certificate applies. An installer that is already on disk and matches its checksum is reused; Cancel stops the download and keeps the part, so Retry continues from the same byte. The check, install and download steps use the long-job IPC budget, release and pack feeds are read in parallel with their own time limits, and after a successful update only the newest two installers stay in `updates/installers`. The source zip merge is for a source checkout and uses the repository layout (`layout: "repo"` in `scanImport`): every file lands where it lives in the repository, root files, `.github`, tooling and `package.json` included, instead of being routed like loose content; files that were removed upstream are kept, and a GitHub update never replaces an existing file under `memory`, `database`, `brain-data`, `conversations`, `security`, `voices`, `downloads`, `logs` or `backup*` (the result counts them as `preserved`). When `package.json`, `package-lock.json`, `kernel/requirements*.txt` or `kernel/pyproject.toml` changed, the result lists the command to run (`npm ci`, `npm run setup:python`); an installed app uses the installer and may only merge content packs through Update content (`github:pull` with `contentOnly`, restricted to `CONTENT_AREAS`: modules, plugins, agents, skills, workflows, resources, docs, and recorded in history without marking the release installed). When a check finds a newer stable release, FRIDAY fetches and verifies its installer in the background (`autoDownload`, on by default, never for a TEST build, never over a download the owner started; the button takes over and resumes it) so Install is instant; only the download happens, the install always waits for the owner. After an update, packages newly added to `kernel/requirements.txt` are installed once into the managed Python (`electron/kernel-deps.cjs`: requirements hash in `updates/kernel-deps.json`, `pip install -r` a minute after start, a failure remembered for a day, restart notice when something was installed; installed app only, a source checkout uses `npm run setup:python`). The release workflow also publishes `FRIDAY-Setup-<version>.exe.blockmap` (one added line in the `for asset in` list of `release.yml`, attached only when the file exists; electron-builder's NSIS target writes it beside the installer). `electron/differential-download.cjs` uses it: with the previous installer on this PC and the block map saved beside it (`<installer>.blockmap`, written after every installer download), only the changed blocks are fetched with HTTP Range (the GitHub redirect is walked once, an expired signed address is refreshed) and the rest is copied from the old file; the rebuilt file must match the published SHA-256, and anything else (no previous installer or block map, a server that ignores Range, too little shared, a mismatch) falls back to the full download, so the first update after this feature ships is a full one. The pre-install safety backup runs on the async file API (`backupStateAsync`) so the window keeps responding, and first checks that the drive can hold it (a plain message and nothing changed otherwise), removes a copy that failed halfway, and after a healthy start older release backups are pruned to the newest two (never the one a pending rollback needs). When the earlier installer has no block map saved beside it (it was downloaded before this existed), it is read from that installer's own release (`/releases/tags/v<version>`, the asset `<installer>.blockmap`) and saved, so the first update can already be a difference. The update path is proven on every built installer by `scripts/verify-update-path.cjs`, which `scripts/verify-build.cjs` runs, so PR Validation (`Verify packaged application`), FRIDAY Release and the CMD pack all prove the same things: the installer has a block map that describes exactly that file; the manifest and `SHA256SUMS.txt` the release would publish (built in a scratch folder with `release-manifest.cjs`, release/ is not touched) list the installer and its block map with the right SHA-256, every published file is one `classifyAsset` recognises and `expectedChecksum` finds the installer; and a differential download rebuilds a changed copy of the real installer over HTTP Range, byte-exact. `verify-build.cjs` also runs `packaged-requires.cjs` against `app.asar` so a module left out of the package fails the PR, not the release. `windows-installer-smoke.ps1` also runs the silent in-place update FRIDAY itself uses (`/S --updated --force-run`): over the install it just made, and, in the `update` scenario (`FRIDAY_SMOKE_SCENARIO`, run by PR Validation's `update-windows` job with `FRIDAY_PREVIOUS_INSTALLER`), over the previously published release and once more while the app is running (the `lifecycle` scenario runs the rest; `all` is the default for a local run); a keep file in each of 12 protected data folders must survive every install, update, keep-uninstall and reinstall. Whether `--force-run` starts the app again is reported, not enforced, until it has been seen on a Windows runner. PR Validation runs every phase of the shared pipeline, so `core/__tests__/build-parity.test.ts` now only asserts that all of them stay covered. A capability that exists both as a built-in (shipped with the installed app) and as a workspace copy keeps the old rule that the workspace copy wins, except when the built-in's version is strictly newer: then the built-in wins and the older copy is reported as `staleOverride` (`electron/capabilities.cjs`), so an old "Update content" merge or an old customisation cannot block what a newer app ships; to keep a customisation, raise its version above the built-in's. The downloader follows redirects by hand and, when a network stack hides the `Location` of a manual redirect, lets it follow the redirect itself. The shipped defaults (`kernel.yaml`, `models.yaml`) reach `<root>/config` through `electron/config-seed.cjs`: copied when missing; replaced (old copy kept as `.bak`) when FRIDAY wrote the current copy and the owner never changed it; otherwise the owner's file stays untouched and the new shipped file is saved beside it as `<name>.new`. What the release workflow publishes (installer, portable, `latest.yml`, `friday-update.json` with SHA-256, `SHA256SUMS.txt`, `CHANGELOG.md`, plus GitHub's source zip) is exactly what `classifyAsset`, `expectedChecksum` and the installer path read; `core/__tests__/release-update-contract.test.ts` pins that against the workflow text without running it. 2026-10-24 research: [GitHub: release assets](https://docs.github.com/en/rest/releases/assets) lists the "Get a release asset" endpoint (Accept `application/octet-stream`, 200 or a 302 to the CDN) as working with fine-grained tokens that have Contents read, so ADOPT the read-only token; the archive (zipball) endpoint's permission page was not read (unverified). [GitHub: REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api) says an authenticated conditional request that returns 304 is not counted against the primary rate limit and that ETags belong to the token that received them, so ADOPT `If-None-Match` keyed by token; its advice to honour `x-poll-interval` is REJECTED because FRIDAY polls hours apart. [electron-updater](https://www.electron.build/docs/api/electron-updater.Class.AppUpdater) defaults to `autoDownload` and `autoInstallOnAppQuit`, with differential downloads from `.blockmap` files and staged rollouts: background download is ADOPTED, install-on-quit is REJECTED (FRIDAY installs only with the owner's go-ahead), staged rollout is REJECTED (single owner), and differential download is ADAPTED (see below): the plan is a port of electron-updater's `computeOperations` (read from `electron-updater@6.8.11` via npm, outside the repo; reuse a block when its checksum and size match), the downloader and the fallbacks are FRIDAY's own. [electron-updater `QuitAndInstallOptions`](https://www.electron.build/docs/api/electron-updater.Interface.QuitAndInstallOptions) documents `isSilent` and `isForceRunAfter` (run the app after a silent install); the switches themselves are confirmed in the installed electron-builder: `NsisTarget.js` registers the flags `updated` and `force-run`, `installSection.nsh` starts the app after a silent assisted install when `isForceRun` is set, `common.nsh` hands `--updated` to the started app, and `uninstaller.nsh` skips data deletion when `isUpdated` (FRIDAY's own `customUnInstall` additionally keeps data unless `/DELETEDATA`). The zipball endpoint's permission page could not be fetched here (unverified), so the first real private-repo source update is the proof, and the failed-install path reopens the old app.

## 8. Python series for the build environment

The floor is `>=3.12.10`. Setup and the installer helper prefer the newest installed series at or below `pythonWheelProven` (3.14), and take a newer series as soon as a pip dry run of `kernel/requirements.txt` with `--only-binary=:all:` passes on it, so a new series is picked up without a config change. When only an unproven newer series is installed, Windows setup first installs the newest proven series from python.org and uses the newer one only if that install fails. The installer helper still uses a newer series when it is the only Python. `FRIDAY_PYTHON` and an existing venv are never second-guessed. The python.org installer list stays inside the proven series and skips a series folder that holds only pre-releases. Code: `scripts/python-runtime.cjs`, `installer/build/install-python.ps1`, `config/toolchain-versions.json`.

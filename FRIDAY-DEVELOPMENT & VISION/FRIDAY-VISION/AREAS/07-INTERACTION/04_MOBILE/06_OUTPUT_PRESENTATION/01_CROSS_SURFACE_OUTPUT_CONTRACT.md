# Cross-Surface Output Contract — What FRIDAY Produces and How It Appears

## Principle
FRIDAY produces one **canonical result**, then projects that result into Chat, Voice, Mobile, desktop UI, notifications, and artifacts according to modality. There is no separate “Chat answer”, “Voice answer”, or “Mobile answer” generated by separate brains.

## Canonical result layers
Every completed turn/task may contain:

1. **Truth state** — what the runtime has verified.
2. **Human explanation** — concise explanation of what happened and why.
3. **Structured data** — tables, lists, JSON, metrics, status, citations.
4. **Artifacts** — files/images/reports/code/exports/media.
5. **Evidence** — sources, tool outputs, verification records, screenshots when applicable.
6. **Action state** — next action, approval required, waiting reason, retry/recovery state.
7. **Presentation hints** — modality-safe rendering preferences; hints never override truth/policy.

## Chat projection
Chat may show:
- rich formatted answer
- headings/lists/tables
- citations/source cards
- inline images
- generated artifact cards
- charts/diagrams
- code blocks
- expandable execution/progress details
- approval controls
- task controls
- evidence/verification details

Chat can display more information than Voice because it has a visual surface.

## Voice projection
Voice prioritizes:
- spoken summary
- short progress preambles when useful
- audible confirmation of important state changes
- concise next action
- interruption-safe speech

When the result is visual or large, Voice should say that a visual/result is available and publish it to the shared surface rather than reading the entire artifact aloud.

If a user asks for detail, Voice can progressively narrate the requested subset.

## Mobile projection
Mobile may show:
- compact answer card
- task timeline
- artifact preview/download
- approval card
- structured data card
- image/chart preview
- source/evidence section
- live progress
- notification/deep link

Mobile can summarize dense desktop content while preserving access to the complete artifact.

## Desktop presentation
The desktop surface may use existing FRIDAY Stage/HUD/chat/activity surfaces to present:
- response
- live execution
- task state
- artifact previews
- visual evidence
- device/screen state
- approval controls

## Notifications
Notifications contain only enough information to explain why the user should open FRIDAY. They are not the canonical result store.

## Artifact-first outputs
If the requested outcome is a file/report/image/diagram/data export, the artifact is the authoritative deliverable. The conversational message explains it and links to it.

## Truth vs presentation
A visual “success” state cannot turn an unverified operation into success. Presentation is always downstream of canonical runtime truth.
